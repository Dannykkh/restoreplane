# 운영 시나리오 — 랜섬웨어 저항 DB 백업 도구

> 대상 산출물: Rust CLI + Tauri 데스크톱 GUI.
> 이 문서는 "운영자가 실제로 겪는 경험"을 기준으로 각 메뉴/명령의 시나리오와 E2E 흐름, 화면 전환을 기술한다.
> 핵심 정서: 랜섬웨어를 겪은(또는 두려워하는) 개인 운영자에게 화면과 명령이 매 순간
> **"복구 가능한가?"**에 답하도록 설계한다. 침착함 = 안심.
> 근거 문서: plan.md, spec.md, flow-diagrams/index.md, sections/index.md, DESIGN.md.

---

## 역할 정의 (개인 운영자 단일 역할, 무인 스케줄러)

이 도구는 멀티유저/RBAC를 v1 범위에서 제외한다(spec.md Out of Scope). 실질 행위 주체는 둘뿐이다.

| 역할 | 정체 | 권한/책임 | 사용 인터페이스 | 신뢰 근원 |
|------|------|-----------|-----------------|-----------|
| **운영자(개인)** | 도구를 설치·설정·복구하는 사람 본인 | 마스터 비밀번호 입력, 복구 코드 오프라인 보관, DB/목적지 등록, 복원 결정, prune 승인 | GUI(주) + CLI(보조/자동화) | 마스터 비밀번호 + 복구 코드(진짜 신뢰 근원) |
| **스케줄러(무인)** | Windows Task Scheduler가 최소권한 계정으로 도구를 호출 | 예약 시각에 `run`만 무인 실행. prune/rotate/복원 권한 없음 | CLI(`dbbackup run` headless) | DPAPI Machine-scope + 비커밋 keyfile entropy(편의 캐시) |

**역할 경계의 핵심 원칙 (plan.md 랜섬웨어 방어)**
- 무인 스케줄러 신원은 **쓰기 전용**이다. 목적지에 대해 PutObject만 가능하고 Delete/lifecycle/retention 변경은 IAM에서 명시 Deny.
- **prune(만료 삭제)는 백업 호스트에서 절대 실행하지 않는다.** 오프호스트 MFA 신원 또는 S3 서버측 lifecycle이 담당하며, 무인 run 프로파일은 prune 자격증명을 로드조차 하지 않는다.
- DPAPI는 "편의 캐시"일 뿐, PC 재설치/이관 시 신뢰 근원이 아니다. 신뢰 근원은 항상 사람이 보관한 비밀번호와 복구 코드다.
- 운영자와 스케줄러는 같은 사람이 소유하지만, **자격증명 권한은 분리**된다(과권한 혼입 = 랜섬웨어 방어 붕괴).

## 메뉴/명령별 시나리오

각 시나리오는 목적 / 사전조건 / 단계(GUI + CLI) / 기대 결과 / 실패 처리 순서로 기술한다.
GUI 화면 이름은 DESIGN.md의 화면 목록(초기 셋업 마법사, DB·목적지 등록, 백업 현황 대시보드, 복원 마법사, 스케줄/알림)을 따른다.

---

### 1. init — 키 셋업 마법사

**목적**: 봉투암호화 신뢰 근원을 최초 1회 구축한다. 마스터 비밀번호에서 KEK를 유도하고, 백업 암호화용 DEK 체계와 3경로 wrapping, 매니페스트 서명키를 만들며, **복구 코드를 1회 표시**한다. 이 단계가 이후 "복구 가능성"의 뿌리다.

**사전조건**
- 도구 최초 설치, 아직 config/키가 없는 상태.
- 운영자가 강한 마스터 비밀번호를 정할 준비가 되어 있고, 복구 코드를 오프라인(종이/금고/패스워드 매니저)으로 보관할 준비가 되어 있다.

**단계 (GUI — 초기 셋업 마법사, 넓은 여백·한 스텝 한 결정·진행 stepper)**
1. `환영` 스텝: "이 도구는 랜섬웨어가 백업까지 망가뜨려도 복구할 수 있게 만듭니다"라는 안심 문구 + 무엇을 만들지(비번/복구코드/DPAPI/서명키) 미리보기.
2. `마스터 비밀번호` 스텝: 비번 입력 + 강도 미터. 약하면 진행 버튼 비활성(마찰). Argon2id 파라미터(m=64MiB,t=3,p=1)는 내부적으로 적용.
3. `복구 코드` 스텝: 고엔트로피 복구 코드를 **1회 표시**하는 경고 모달. "이 화면은 다시 볼 수 없습니다. 지금 오프라인으로 적으세요"라는 강한 안내. `복사함/적어둠` 체크박스를 명시적으로 눌러야 다음 진행(미보관 시 진행 차단 옵션).
4. `무인 실행(DPAPI)` 스텝: "PC가 잠긴 채 예약 백업이 돌게 할까요?" 토글. 등록 시 DPAPI Machine-scope + 비커밋 keyfile entropy 생성.
5. `서명키` 스텝: 오프라인 ed25519 개인키/공개키 생성 안내(매니페스트 위조 방지의 근거). 개인키는 리포 밖 로컬 보관.
6. `왕복 검증` 스텝: config secret 필드를 DEK로 암호화 후 즉시 복호화하는 자가 테스트를 실행해 초록 dot으로 "키 체계 정상" 확인.

**단계 (CLI)**
```
dbbackup init
  → 비번 입력(TTY, 에코 없음)
  → 복구 코드 출력(stdout 1회, "--- WRITE THIS DOWN ---" 배너)
  → --register-dpapi 여부 프롬프트(또는 플래그)
  → ed25519 keypair 생성, config roundtrip 자가 테스트 결과 출력
```

**기대 결과**
- 리포/로컬에 [wrapped DEK 3종(비번/복구코드/DPAPI)] + [서명 공개키] + [암호화된 config]만 생성. 평문 secret·개인키·keyfile·복구코드는 `.gitignore`로 리포 밖.
- 왕복 암복호화 성공 = "이 키로 만든 백업은 이 비번 또는 복구 코드로 반드시 열린다"가 증명됨.

**실패 처리**
- 약한 비번: 거부 + 이유 표시(진행 차단).
- 복구 코드 미확인(체크박스 미클릭): 다음 스텝 차단. GUI는 "복구 코드 없이 진행하면 비번 분실 시 영구 복구 불가"를 붉은 배지가 아닌 절제된 warning 톤으로 경고.
- DPAPI 등록 실패: 치명 아님. "무인 자동실행 대신 매 실행마다 비번 입력" 폴백 안내 후 나머지 진행.
- 왕복 검증 실패: 하드 정지. 부분 생성 키 정리 후 재시도 안내(신뢰 근원이 깨진 채로 진행 금지).

### 2. doctor — 환경/전제 진단

**목적**: 백업이 실제로 성공할 수 있는 상태인지 사전 종합 점검. 덤프 도구 버전 매트릭스, DPAPI 접근, 서명키 존재, 목적지 도달성, append-only 자격증명 정합을 한 번에 확인해 "예약 시각에 조용히 실패"를 예방한다.

**사전조건**: init 완료. 최소 하나 이상의 DB/목적지 등록(없으면 해당 항목은 스킵 표시).

**단계 (GUI)**
1. 대시보드 상단 `진단 실행` 또는 설정 메뉴에서 진입.
2. 체크 항목이 리스트로 순차 실행되며 각 항목에 초록/노랑/빨강 dot + 기술값(모노스페이스: 감지된 pg_dump 버전, 서버 버전, 버킷 versioning 상태 등).
3. 문제 항목은 "무엇을/왜/어떻게 고치나"를 인라인으로 펼침.

**단계 (CLI)**
```
dbbackup doctor            # 전체
dbbackup doctor --db pg1   # 특정 대상만
dbbackup keys status       # 키/서명키/DPAPI 등록 상태만
```

**점검 항목(대표)**
- 번들 덤프 도구 존재 및 버전(pg_dump/pg_dumpall/mysqldump), 서버 메이저 대비 client_major >= server_major.
- DPAPI Machine-scope로 KEK 복원 가능 여부(무인 경로 살아있나).
- ed25519 서명 개인키 접근 가능 여부.
- 목적지 도달성 + 능력(DestCaps: immutability 모드, checksum_required, versioning ON, 기본 보존).
- append-only 자격증명 정합(과권한/미잠금 조기 경고).

**기대 결과**: 모든 항목 초록이면 "예약 백업이 조용히 실패할 이유 없음" 상태. 노랑/빨강은 스케줄 무인 실행 전에 사람이 개입할 지점을 명확히 제시.

**실패 처리**: 빨강 항목이 하나라도 있으면 "이 상태로 예약하면 무인 실행이 실패한다"를 경고. doctor 자체는 비파괴적 — 어떤 것도 바꾸지 않고 진단만.

### 3. test-connection — 연결 테스트

**목적**: DB/목적지 등록 전후에 접속 자격증명·네트워크·SSH 터널·host-key 핀이 실제로 통하는지 즉시 확인. "등록은 됐는데 백업 때 접속 실패"를 방지.

**사전조건**: 대상 DB 또는 목적지 정보 입력(등록 전 임시값도 가능).

**단계 (GUI — DB·목적지 등록 화면, 인라인 피드백)**
1. 등록 폼에서 호스트/포트/자격증명(또는 SSH 바스티온) 입력.
2. `연결 테스트` 버튼 → 성공 시 초록 dot + 감지된 서버 버전/능력 배지, 실패 시 붉지 않은 절제된 오류 + 원인.

**단계 (CLI)**
```
dbbackup test-connection --db pg1
dbbackup test-connection --dest s3-primary
```

**기대 결과**
- DB: 접속 성공 + 서버 버전 감지 + (SSH면) host-key 지문 표시 및 핀 저장 여부 확인.
- 목적지: 쓰기 가능 + 능력(Object Lock 모드, versioning, checksum) 표시. S3면 이 시점에 불변성 capability 배지.

**실패 처리**
- 인증 실패/타임아웃/호스트 키 불일치를 구분해 메시지. host-key가 핀과 다르면 **하드 경고**(중간자 가능성) 후 사용자 확인 없이는 저장 금지.
- 실패해도 비파괴적. 등록 자체는 사용자가 재시도 후 진행.

### 4. add-db — 백업 원본 등록

**목적**: PostgreSQL/MySQL(MariaDB) 서버를 백업 대상으로 등록. 접속 방식(직결/SSH 터널), 버전, 엔진 특성을 수집해 이후 무인 run이 정확한 도구·플래그로 덤프하도록 한다.

**사전조건**: init 완료(config secret을 DEK로 암호화 저장하기 위함).

**단계 (GUI — DB·목적지 등록, 중간 밀도)**
1. `DB 추가` → 엔진 선택(Postgres/MySQL) → 접속 정보 입력.
2. 직결 vs SSH 터널 선택. SSH면 바스티온 host-key 핀.
3. `연결 테스트`(위 3번) 인라인 실행 → 서버 버전/엔진 스캔 결과 표시(MySQL이면 스토리지 엔진 스캔: MyISAM 등 non_transactional 경고).
4. 저장 시 자격증명 필드가 `enc:...`로 DEK 암호화되어 config에 기록.

**단계 (CLI)**
```
dbbackup add-db --engine postgres --host ... --tunnel ssh://bastion ...
dbbackup add-db --engine mysql --host ...
```

**기대 결과**
- config에 DB 항목 추가(secret은 암호화). PostgresSource는 globals(pg_dumpall --globals-only) 처리를 1급으로 기록, MySqlSource는 엔진 스캔·플래그(--single-transaction 등) 기록.
- 등록 직후 doctor/test-connection이 초록이면 "이 DB는 무인 백업 준비 완료".

**실패 처리**
- 버전 불일치(client_major < server_major) 감지 시 저장은 하되 **경고 플래그**를 남겨 doctor/run에서 하드 페일하도록 표시.
- MyISAM 등 비트랜잭션 테이블: 백업 중 DDL 비일관 위험을 경고하고 백업 창 DDL 회피 안내.

### 5. add-dest — 목적지 등록

**목적**: 오프사이트 목적지를 등록. S3(Object Lock), SSH(SFTP), 로컬/NAS 세 종류. 랜섬웨어 방어의 실체(불변성)를 여기서 확정한다.

**사전조건**: init 완료. S3면 append-only 쓰기 자격증명(PutObject only)과 Object Lock 버킷이 준비돼 있어야 이상적.

**단계 (GUI)**
1. `목적지 추가` → 종류 선택(S3/SSH/Local).
2. S3: 엔드포인트/버킷/쓰기 자격증명 입력 → `연결 테스트`가 versioning ON, Object Lock 모드(Governance 권장), 기본 보존기간, checksum 지원을 감지해 **불변성 capability 배지**로 표시.
3. SSH: 호스트/경로 + host-key 핀. Local: 폴더 경로(최소 방어선, 스풀 겸용).
4. Governance vs Compliance 선택 시 Compliance는 "자기잠금 위험"을 명시 경고하고 opt-in 재확인.

**단계 (CLI)**
```
dbbackup add-dest --type s3 --bucket ... --endpoint ... --object-lock governance
dbbackup add-dest --type ssh --host ... --path ...
dbbackup add-dest --type local --path D:\backup-spool
```

**기대 결과**
- 목적지가 config에 등록되고 DestCaps가 기록됨. S3면 대시보드/목적지 카드에 "불변(Object Lock)" 배지.
- 여러 목적지 등록 시 run에서 팬아웃 업로드(옵션 C) 대상이 됨.

**실패 처리**
- versioning OFF이거나 Object Lock 미설정 S3: "이 버킷은 랜섬웨어에 삭제될 수 있습니다"를 절제된 warning으로 경고하고 IAM 정책 템플릿 링크 제공.
- 쓰기 자격증명에 Delete/lifecycle 권한이 섞여 있으면(과권한) **거부 또는 loud-warn** — append-only 원칙 위반.

### 6. run — 백업 실행

**목적**: 등록된 DB를 덤프→해시→압축→암호화→로컬 스풀→서명 매니페스트→다중 목적지 업로드→자동 검증(L1/L2)까지 수행. 무인 스케줄러가 호출하는 핵심 명령이며, 매 실행마다 랜섬웨어 방어 자가 테스트를 곁들인다.

**사전조건**: init + 최소 1개 DB + 최소 1개 목적지. 무인 경로면 DPAPI로 KEK 복원 가능.

**단계 (GUI — 대시보드, 높은 밀도)**
1. 대시보드 job 카드에서 `지금 백업` 또는 전역 `모두 백업`.
2. 진행 로그 스트리밍: plan(globals+dbs / 엔진 스캔) → 버전 재검증 → 덤프 → blake3 tee → zstd → age(백업별 DEK) → 스풀 커밋 → 서명 → 목적지별 병렬 업로드(진행률) → 자동 검증 L1/L2.
3. 완료 시 카드가 "마지막 백업 시각 + 검증 레벨 배지 + 불변성 배지 + 다음 예약"으로 갱신. 상단 "모두 정상" 안심 헤더.

**단계 (CLI)**
```
dbbackup run                 # 전체
dbbackup run --db pg1        # 특정 DB
dbbackup run --dry-run       # 계획/검증만, 실제 업로드 없음
```

**파이프라인 핵심 (plan.md 옵션 C + Commit Protocol)**
- 매 run 버전 재검증: client_major >= server_major 아니면 HARD FAIL.
- Commit Protocol: 자식 exit code 확인 → finish 순서 zstd→age→스풀 flush. "복사~커밋" 사이 early-return 금지(절단 백업 방지).
- 매 run 불변성 자가 테스트: probe key로 DeleteObject/PutLifecycle 시도 → 거부 확인, versioning ON + 기본 보존 확인. 과권한/미잠금이면 refuse/loud-warn.
- 팬아웃: 목적지별 독립 업로드(JoinSet), 목적지별 retry/resume, **부분 성공 리포트**.

**기대 결과**
- 각 목적지에 암호문 객체 + 서명 매니페스트 업로드. Catalog(SQLite)에 backups/artifacts 기록(진실 소스는 동봉 매니페스트).
- 자동 검증 L1(재복호+재해제+평문 blake3 대조), L2(pg_restore --list) 통과 → 카드에 검증 배지.

**실패 처리**
- DB 접속 실패/버전 불일치: **해당 DB만 실패 격리**, 나머지 진행, 종료코드 + 알림.
- 목적지 일부 단절: 재시도/재개, 부분 객체 정리. 하나만 실패 시 "부분 성공"으로 명확히 리포트(초록 아님, 오렌지).
- 불변성 자가 테스트 실패(삭제가 허용됨): 백업 데이터는 올리되 **loud-warn** — "이 목적지는 랜섬웨어에 취약"을 대시보드에 남김.
- finish 누락/절단 위험: RAII로 finish 강제, 실패 시 해당 백업을 커밋하지 않음(죽은 백업 방지).

### 7. verify — 백업 검증

**목적**: 백업이 "죽은 백업"이 아님을 실제로 증명. L1(평문 해시 대조), L2(구조 목록), L3(임시 인스턴스 전체 복원 + 스키마 해시 + 행 수)를 골라 수행하고 결과를 catalog에 verified/레벨로 기록.

**사전조건**: 검증할 백업이 목적지 또는 스풀에 존재. L3는 임시 인스턴스(로컬/Docker) 가용.

**단계 (GUI)**
1. 대시보드 백업 항목 → `검증` → 레벨 선택(L1 빠름 / L2 구조 / L3 완전 복원).
2. 서명 검증 게이트 통과 후 진행 로그. L3는 샌드박스에서 복원 진행 상태 표시.
3. 완료 시 "L3 복원 통과" 배지 + 검증 시각(모노스페이스).

**단계 (CLI)**
```
dbbackup verify --backup <id> --level l1|l2|l3
dbbackup verify --latest --level l3
```

**기대 결과**
- L1: 재복호→재해제→평문 blake3가 매니페스트 값과 일치.
- L2: pg_restore --list로 구조 파싱 성공.
- L3: 샌드박스(임시·아웃바운드 차단·비특권·local_infile=0·COPY PROGRAM 차단·pg_restore --no-privileges·슈퍼유저 금지)에 전체 복원 후 스키마 해시/행 수 대조.
- catalog에 verified + 레벨 기록 → 대시보드가 "이 백업은 실제로 복원된다"를 배지로 답함.

**실패 처리**
- 서명 검증 실패: **하드 거부**(미서명/위조 매니페스트). danger 배지.
- 체크섬 불일치/복원 실패: 해당 백업을 unverified로 표시 + 알림. 운영자에게 "다른 시점 백업으로 대체 검증" 유도.

---

### 8. restore — 복원 마법사

**목적**: 실제 재난(랜섬웨어) 또는 실수 삭제 후 데이터를 되살린다. 서명 검증 게이트 → DEK unwrap(비번/복구코드/DPAPI 중 가용 경로) → 복호화→해제→샌드박스 또는 지정 대상 복원. 이 도구의 존재 이유가 실현되는 지점.

**사전조건**: 복원할 백업 접근 가능. 마스터 비밀번호 **또는** 복구 코드 보유(비번 분실 시 복구 코드 경로).

**단계 (GUI — 복원 마법사, 넓은 여백·위험 경고)**
1. `복원` → 대상 백업 선택(카탈로그/목적지에서 시점 선택).
2. `서명 검증` 게이트 화면: 매니페스트 ed25519 서명 통과해야 다음 진행(통과 = 신뢰 배지, 실패 = 진행 차단).
3. `키 경로` 화면: 이 PC의 DPAPI가 없으면(새 PC) 비밀번호 또는 복구 코드 입력 선택.
4. `복원 대상` 화면: 샌드박스(검증용) vs 실제 DB(운영 복구). 실제 대상은 **문구 재입력 마찰** + 덮어쓰기 경고.
5. 복원 진행 로그(샌드박스 격리 상태 명시) → 완료 시 행 수/체크섬 요약.

**단계 (CLI)**
```
dbbackup restore --backup <id> --to sandbox
dbbackup restore --backup <id> --to <target-db> --recovery-code   # 비번 분실 경로
```

**기대 결과**
- 서명 검증 통과 → DEK unwrap 성공 → age 복호화 → zstd 해제 → untar → 대상에 복원.
- 다른 PC/복구 코드 경로로도 동일하게 복원 성공(이식성 증명).

**실패 처리**
- 서명 검증 실패: 진행 불가(위조 가능성). 원본 목적지에서 다른 시점 재시도 안내.
- DEK unwrap 실패(비번/복구코드 오입력): 재입력. 세 경로 모두 실패면 "이 백업은 이 키셋으로 열 수 없음"을 정직하게 안내.
- 실제 DB 복원 중 오류: 샌드박스 선복원으로 안전 확인 후 재시도 권장. 부분 복원 방지.

---

### 9. rotate-key — 키/비밀번호 회전

**목적**: 마스터 비밀번호 변경, 복구 코드 재발급, 서명키 교체, DPAPI 재등록. 자격증명 노출 의심·정기 위생·PC 이관 후 재캐시에 사용. 기존 백업의 복원 가능성을 깨지 않는 것이 최우선.

**사전조건**: 현재 비밀번호 또는 복구 코드로 인증 가능.

**단계 (GUI)**
1. 설정 → `키 관리` → 회전 대상 선택(비번/복구코드/서명키/DPAPI).
2. 현재 인증 → 새 값 입력. 복구 코드 재발급이면 다시 1회 표시 경고 모달.
3. 회전 후 왕복 검증 + 기존 백업 샘플 복호 테스트로 "옛 백업도 여전히 열린다" 확인.

**단계 (CLI)**
```
dbbackup rotate-key --master-password
dbbackup rotate-key --recovery-code
dbbackup rotate-key --signing-key
dbbackup register-dpapi        # 새 PC에서 DPAPI 캐시 재등록
```

**기대 결과**
- 새 비번/코드로 DEK를 다시 wrap(기존 DEK 유지 시 옛 백업 호환 유지, 또는 신규 DEK 정책에 따라 리랩). 서명키 교체 시 새 공개키로 이후 매니페스트 서명, 과거 매니페스트는 옛 공개키로 검증 가능하도록 키 이력 보존.
- DPAPI 재등록으로 무인 경로 복구.

**실패 처리**
- 현재 인증 실패: 회전 거부.
- 회전 후 옛 백업 복호 테스트 실패: **롤백** — 기존 wrap 유지, 회전 중단(복원 가능성 손상 방지).
- 서명키 교체 시 공개키 이력 미보존 경고: 과거 백업 검증 불가 위험을 하드 경고.

### 10. prune — 만료 삭제 (격리 실행)

**목적**: 보존기간이 만료된 오래된 백업을 정리. **랜섬웨어 방어상 백업 호스트에서 실행 금지** — 별도 격리 신원(오프호스트 MFA) 또는 S3 서버측 lifecycle로만 수행. 무인 run 프로파일은 이 명령의 자격증명을 로드하지 않는다.

**사전조건**: 별도 prune 프로파일(MFA/오프호스트 신원). Object Lock Governance 보존기간 만료 대상.

**단계 (GUI — 위험 액션, 최대 마찰)**
1. 별도 `보관 관리(격리)` 화면. 기본적으로 백업 호스트 GUI에서는 **비활성** 또는 "이 작업은 격리 신원에서만"이라는 안내.
2. 삭제 후보 목록(보존 만료분만) + 각 항목 보존기한(모노스페이스).
3. 실행 시 문구 재입력 + MFA 확인. Compliance 모드 객체는 만료 전 삭제 불가임을 명시.

**단계 (CLI — 격리 프로파일 전용)**
```
dbbackup prune --profile offhost-mfa --older-than 90d --dry-run
dbbackup prune --profile offhost-mfa --older-than 90d --confirm
```

**기대 결과**
- 보존기간 만료 객체만 삭제. versioning/Object Lock으로 만료 전 객체는 애초에 삭제 거부됨.
- 삭제 내역이 감사 로그에 남고 catalog가 rebuild로 정합화됨.

**실패 처리**
- 백업 호스트/무인 신원으로 시도: **원천 거부**(자격증명 부재). 이것이 정상 동작 — "삭제 권한이 없어서 랜섬웨어도 못 지운다".
- 보존기간 미만 삭제 시도: 목적지가 Deny. dry-run으로 항상 사전 확인 권장.

### 11. catalog rebuild — 카탈로그 재구성

**목적**: 로컬 SQLite 카탈로그가 손상/변조/유실됐을 때, 목적지에 동봉된 **서명 매니페스트(진실 소스)**로부터 백업 이력을 재구성. catalog는 캐시일 뿐이며 매니페스트가 권위를 가진다(H5 대응).

**사전조건**: 목적지 접근 가능. 매니페스트 서명 검증용 공개키 보유.

**단계 (GUI)**
1. 설정 → `카탈로그` → `목적지에서 재구성` → 소스 목적지 선택.
2. 매니페스트 수집 → 서명 검증 → 통과분만 카탈로그에 반영. 진행/결과 요약.

**단계 (CLI)**
```
dbbackup catalog rebuild --from s3-primary
dbbackup catalog rebuild --from ssh-offsite
```

**기대 결과**
- 로컬 catalog가 목적지의 실제 백업 상태와 일치. 변조된 로컬 catalog가 있었어도 서명 매니페스트 기준으로 교정.

**실패 처리**
- 서명 검증 실패 매니페스트: 카탈로그에 반영하지 않고 격리 보고(위조 의심).
- 목적지 접근 실패: 다른 목적지에서 rebuild 시도 안내(다중 목적지의 이점).

### 12. schedule — 무인 스케줄 등록

**목적**: Windows Task Scheduler에 `run`을 등록해 정해진 시각 무인 백업. StartWhenAvailable로 PC가 꺼져 있던 시간도 catch-up, overlap guard로 중복 실행 방지.

**사전조건**: init에서 DPAPI 등록 완료(무인 KEK 복원). 최소권한 실행 계정.

**단계 (GUI — 스케줄/알림, 중간 밀도)**
1. `스케줄` → cron/주기 입력 → **cron 프리뷰**(다음 실행 시각들 미리보기).
2. RPO 한계 명시 배너("논리 덤프 주기 = 최악의 경우 이만큼 데이터 손실 가능").
3. 알림 채널 설정(webhook/email) — 실패 시 통지.
4. 저장 시 schtasks XML(StartWhenAvailable) 등록.

**단계 (CLI)**
```
dbbackup schedule --cron "0 3 * * *" --start-when-available --notify webhook:https://...
dbbackup schedule --list
dbbackup schedule --remove <task>
```

**기대 결과**
- Task Scheduler에 작업 등록. 예약 시각에 무인 run 실행, overlap guard(named mutex/runs unique index)로 중복 방지.
- 부팅 지연/절전 후에도 catch-up 실행. 실패 시 알림 발송.

**실패 처리**
- DPAPI 미등록 상태로 예약: "무인 경로 없음 → 예약 실행이 비번 프롬프트에서 멈춘다"를 하드 경고, 등록 유도.
- 등록 시각 겹침: overlap guard가 두 번째 실행을 스킵하고 로그 남김.
- 예약 중 PC 꺼짐: 재부팅 후 StartWhenAvailable로 밀린 백업 catch-up(아래 E2E 4 참조).

## E2E 시나리오

### E2E-1. 최초 셋업 → 첫 백업 → 검증

**상황**: 랜섬웨어가 두려운 개인 운영자가 도구를 처음 깐다. 목표는 "내 DB가 안전하게 백업되고, 그게 진짜 복원된다"를 두 눈으로 확인하는 것.

1. **init(키 셋업 마법사)**: 마스터 비번 설정 → 복구 코드 1회 표시받아 종이에 적고 금고에 → DPAPI 등록(무인 준비) → 서명키 생성 → 왕복 검증 초록. 내부 정서: "복구의 열쇠를 내가 손에 쥐었다".
2. **add-db**: Postgres 서버 등록, test-connection 초록 + 서버 버전 감지. (MySQL도 동일 반복 가능)
3. **add-dest**: S3(Object Lock Governance) 등록 → 불변성 capability 배지 확인 + 로컬 NAS를 최소 방어선으로 추가.
4. **doctor**: 전체 초록 — 덤프 도구 버전 OK, 목적지 versioning ON, append-only 정합.
5. **run**: 대시보드에서 `지금 백업` → 파이프라인 로그가 흐르고, 불변성 자가 테스트가 "삭제 거부됨"을 확인 → 다중 목적지 업로드 → 자동 L1/L2 통과. 카드에 "불변" + "L2" 배지.
6. **verify --level l3**: 샌드박스에 전체 복원 + 행 수 대조 통과 → "L3 복원 통과" 배지. 운영자는 이제 "백업이 있는데 못 쓰는" 공포에서 벗어난다.

**기대 최종 상태**: 대시보드 상단 "모두 정상" 헤더, 각 job 카드에 최근 백업 시각 + 불변 배지 + 검증 레벨 배지 + 다음 예약.

---

### E2E-2. 랜섬웨어 발생 → 다른 PC에서 복구 코드로 복원

**상황**: 랜섬웨어가 운영 서버와 백업 PC를 모두 암호화했다. 백업 PC가 못 쓰게 됐고 DPAPI 캐시도 함께 사라졌다. 운영자에게 남은 것은 **오프사이트 S3의 불변 백업**과 **금고 속 복구 코드**뿐이다.

1. **불변성 덕분에 백업 생존**: 랜섬웨어의 쓰기 자격증명은 PutObject only였고 Object Lock Governance가 걸려 있어, S3의 백업 객체는 삭제/암호화되지 않았다. (매 run 자가 테스트가 이 상태를 사전 보증해왔다.)
2. **새(깨끗한) PC에 도구 설치**: 코드는 공개 리포에서, 암호화 config도 리포/오프사이트에서 가져온다. 평문 secret은 없다.
3. **restore(복원 마법사)**: 대상 백업 시점 선택 → **서명 검증 게이트** 통과(위조 아님 확인).
4. **키 경로 = 복구 코드**: 새 PC엔 DPAPI 캐시가 없고 마스터 비번을 잊었다고 가정 → 금고 속 **복구 코드** 입력 → DEK unwrap 성공.
5. **샌드박스 선복원**으로 안전 확인(행 수/체크섬) → 이후 깨끗한 운영 DB로 실복원(문구 재입력 마찰).
6. **rotate-key**: 사고 후 위생을 위해 마스터 비번 재설정 + 복구 코드 재발급 + 새 PC에 DPAPI 재등록(register-dpapi).

**기대 최종 상태**: 다른 PC·다른 신원 근원(복구 코드)만으로 데이터 복원 성공. "이식성 있는 신뢰 근원"이 실제로 작동함을 증명. 이 시나리오가 프로젝트 존재 이유.

---

### E2E-3. 서버 메이저 업그레이드 후 버전 불일치 감지

**상황**: 운영자가 Postgres 서버를 15 → 16으로 올렸다. 번들된 pg_dump는 아직 15다. 이대로 무인 백업이 돌면 덤프가 실패하거나(또는 최악의 경우 손상 덤프) "죽은 백업"이 될 수 있다.

1. **다음 무인 run 진입 시 버전 재검증**: 매 run은 client_major >= server_major를 재확인한다. pg_dump(15) < 서버(16) → **HARD FAIL**로 즉시 정지, 손상 덤프를 만들지 않음.
2. **알림 발송**: 스케줄 실패 알림(webhook/email)이 "pg1: client_major 15 < server_major 16, 백업 스킵됨"을 통지. 해당 DB만 격리 실패, 다른 DB는 정상 진행.
3. **doctor로 확인**: 운영자가 `doctor --db pg1` 실행 → 버전 매트릭스 항목이 빨강, 감지된 서버/클라이언트 버전을 모노스페이스로 표시.
4. **해결**: 번들 버전 매트릭스에서 pg_dump 16을 선택/갱신하도록 도구가 안내(하이브리드 폴백). 갱신 후 doctor 초록.
5. **run 재실행**: 이제 client_major >= server_major → 정상 백업 + 검증 통과.

**기대 최종 상태**: 버전 불일치가 "조용한 실패"가 아니라 **명시적 하드 페일 + 알림 + 진단**으로 드러남. 운영자는 손상 백업이 아니라 "일시적으로 스킵된 백업"을 다룬다.

---

### E2E-4. 스케줄 무인 백업 catch-up

**상황**: 매일 03:00 예약 백업. 그런데 그 시간에 PC가 절전/종료 상태였다. 운영자는 "오늘 백업이 빠졌나?" 불안하다.

1. **StartWhenAvailable**: schtasks XML에 StartWhenAvailable이 설정돼, PC가 03:00에 꺼져 있었어도 다음 부팅/가용 시점에 **밀린 작업을 catch-up 실행**한다.
2. **overlap guard**: 만약 수동 run과 catch-up이 겹치면 named mutex(또는 runs unique index)가 두 번째를 스킵하고 로그를 남긴다(중복·경쟁 방지).
3. **무인 경로 정상 동작**: DPAPI Machine-scope로 KEK 복원 → DEK unwrap → config 복호 → 백업. 사람 개입 없이 완료.
4. **결과 통지 + 대시보드 반영**: 성공 시 카드의 "마지막 백업 시각"이 catch-up 시각으로 갱신, 실패 시 알림. 운영자가 아침에 대시보드를 열면 "밀렸지만 따라잡았음"이 명확.

**기대 최종 상태**: 절전/종료로 놓친 백업이 방치되지 않고 자동 만회됨. RPO 배너로 "최악의 경우 손실 창"이 사전 고지돼 있어 운영자의 기대와 실제가 어긋나지 않는다.
